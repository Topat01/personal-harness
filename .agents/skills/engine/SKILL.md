# engine (엔진)

목적: 과제의 핵심을 **작고 검증 가능하게** 만든다. 시작 전에 `NOTES.md` 2절(반드시 지킬 것, 줄이거나 늘릴 것, 지표·퇴화 경고 기준, 기초안)이 비어 있으면 만들지 말고 사람에게 채워 달라고 한다.

1. 입력 읽기: 원본은 수정하지 않는다. 버리거나 바꾼 입력은 사유별 건수를 출력한다. 시각은 읽을 때 한 형식으로 맞추고, 순서가 섞여 들어와도 정렬해 처리한다. 같은 기록이 다시 들어와도 결과가 늘지 않게 기록의 고유 키를 정한다.
2. 기초안: `NOTES.md` 2절에 적힌 방법 그대로. 규칙을 지키면서 **퇴화하지 않는** 단순한 방법이어야 한다(규칙만 지키고 잘게 쪼갠 해는 실패).
3. 잣대 두 개를 해법과 분리된 모듈로 만든다: `validate(result, inputs) -> 위반 목록`(`SPEC.md` 2절 H규칙), `evaluate(result, inputs) -> 지표`(`NOTES.md` 2절 지표). 어떤 후보 해법이든 같은 잣대로 채점할 수 있게 하고, 테스트·화면·내보내기에서 같이 쓴다.
4. 지표: 실행할 때마다 `NOTES.md` 2절의 지표를 출력한다(최적화 성격이면 목표 값, 단위별 활용률 평균·최소, 저활용 단위 수 등. 판정·알림형이면 알림 수(근무자·시간당), 놓친 건수, 정답 기록이 있으면 정밀도·재현율). 퇴화 경고 기준을 넘으면 **결과를 쓰지 말고 멈추고 보고**한다. 보고에는 그룹별(예: 사업장×근무시간대) 분포를 붙여 원인이 방법인지 데이터 구조인지 보이게 한다. 사람이 "기록하고 진행"을 정하면 같은 경고로 다시 멈추지 않는다(숫자만 NOTES에 기록).
5. 내보내기: 형식(스키마)이 주어졌으면 그 형식 그대로, 그리고 내보낸 실제 출력을 검증 함수로 한 번 검사한다.
6. 테스트는 최대 3개: 규칙 위반을 잡는지 1개, 경계 입력 1개, 입력부터 내보내기까지 흐름 1개. 기대값은 구현과 다른 방법(손 계산·원본 직접 집계)으로 구한다.
7. 뼈대에 연결: 화면·내보내기에서 이 엔진을 호출하게 한다. 실제로 한 번 실행해 결과와 지표를 보고한다.
8. `SPEC.md` 상태 갱신 → AGENTS.md 4절 형식으로 설명(채팅 5줄, NOTES 4절 3줄 + 빈 `내 말:`) → 커밋. 필수 산출물이 다 갖춰졌고 퇴화 경고가 없으면 `git tag submittable-v1`을 제안한다.

후보 해법 탐색(AGENTS 3절 5단계)은 이 스킬에서 하지 않는다. 기초안이 확인된 뒤 사람이 요청하면 같은 `evaluate`로 비교한다.
