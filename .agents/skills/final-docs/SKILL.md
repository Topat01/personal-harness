# final-docs

## 1. 근거 모으기 (실행해서 확인)
- `git log --oneline`, 테스트 실행 결과, 실제 실행·접속 명령이 동작하는지
- `SPEC.md`(H·R 상태, Q 답)와 `NOTES.md` 전체(확인한 것, 기준, 모듈 지도, 대표 흐름, 단계별 기록, 엣지케이스·AI가 틀린 곳)

## 2. 지시문이 요구한 문서를 모두 쓰기
- 양식(제목·순서)이 주어졌으면 그대로 쓰고, 해당 없는 항목은 "해당 없음". 지시문 파일 자체는 수정하지 않는다.
- 실행 안내: 다른 사람이 처음부터 따라 할 수 있는 설치·환경변수(값 제외)·실행·접속·테스트 명령, 역할별 이용 순서, 데이터 준비·오류 확인 방법, 판단 기준과 최적화 방식(NOTES 2절의 기초안→개선안 비교 수치).
- AI 협업 문서: NOTES 6절 [AI] 줄의 실제 사례로 쓴다(무엇이 문제였고, 어떻게 알아챘고, 어떻게 확인·해결했나). 일반론 금지.
- 확인하지 않은 내용은 쓰지 않는다. 사람이 정한 것과 AI가 제안한 것을 구분한다.

## 3. 예상 질문 (NOTES.md 8절)
아래 6유형마다 질문 1개와 **핵심어 3~4개**(파일·함수 이름, 숫자, 버린 방법, 약한 곳)만 쓴다. 답 문장은 쓰지 않는다(사람이 말해 본다).
1. 모듈 간 동작과 경계 2. 테스트와 다른 사람의 재현 3. 운영 중 중복 요청·처리 중 실패 4. 기초안→개선안 이유와 효과 5. 까다로운 엣지케이스 6. AI가 만든 코드에서 검증·발견한 것
NOTES 4절의 `내 말:` 줄을 코드와 대조해 틀린 것만 짚고, 비어 있는 단계는 예시로 짧게 다시 설명한다.

## 4. 점검
`python3 <kit>/tools/check_submit.py <필수 산출물…>`(Dockerfile이 있으면 `--docker`) 실행 결과를 보고한다. 컨테이너를 실제로 못 띄우면 Dockerfile이 지금 소스 파일과 데이터를 모두 포함하는지 직접 대조한다(빌드는 되는데 실행 때 모듈이 없는 경우가 흔하다). `SPEC.md`에서 `[x]`가 아닌 H·R이 있으면 함께 보고한다(못 한 것은 남은 한계로). 화면·서버가 있으면 실제로 띄워 확인했는지 묻는다.
