# design-review

## 입력
- 사람이 쓴 구조안(몇 줄이어도 됨)
- 과제 안내의 필수조건·제출물, `PLAN.md`의 성공 기준·확인한 조건·안 만들 것

## 절차
1. 요구사항을 한 줄씩 적고, 구조안의 어느 부분이 그것을 맡는지 대응시킨다. 대응이 없는 요구 = **빠진 것**, 대응되는 요구가 없는 부분 = **과설계 후보**.
2. 문제 될 곳을 찾는다: 경계·빈 입력·형식이 깨진 입력, 시간·단위 기준, 상태가 섞이는 곳, 실행 환경 제약(패키지·포트·0.0.0.0).
3. 같은 요구를 더 적은 코드로 만족하는 방법이 있으면 한 가지만 제시한다.
4. 가장 작은 끝까지 도는 버전(E2E v0)을 한 줄로 제안한다.

## 출력 (10줄 이내)
```
빠진 요구: …
과설계 후보: … (이유: 요구에 없음 / 합의한 "안 만들 것")
문제 될 곳: … → 테스트로 막을 방법
더 단순한 안: …
E2E v0: …
```

## 금지
- 코드 수정, 파일 생성. 사람이 결정하기 전에는 아무것도 바꾸지 않는다.
- 요구에 없는 "확장성·범용성"을 이유로 구조를 키우자고 제안하기.
